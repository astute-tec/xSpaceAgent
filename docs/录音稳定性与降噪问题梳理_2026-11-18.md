# 录音稳定性与降噪问题梳理（2026-11-18）

> 范围：`firmware/wifi-provision/`、`hub/`、部署包与当前设备运行状态。
> 本轮只做分析、构建核验和只读式设备诊断，不刷机、不修改业务代码。

## 1. 结论先行

当前系统已经具备“能录、能存、能上传、能转写”的演示能力，但还不能按“录音稳定、数据不丢、远场可用”验收。

最优先的问题不是继续调一个降噪参数，而是先修正采集格式、音频时序和离线队列。当前至少存在三类会直接破坏录音的 P0 问题：

1. **ES7210 输入格式与原厂实现不一致，存在 8/16-bit 配置错配风险。**
2. **AFE 输出队列会在待机时积累旧音频，开始录音后可能先读旧数据并丢新数据。**
3. **25MB Flash 按当前 PCM WAV 只能存约 13–15 分钟，不是文档中的 14 小时；空间不足时实际丢最新录音。**

因此整改顺序必须是：

```
采集格式正确 → 时间窗口正确 → 本地落盘不丢 → 再比较 NS/AGC/AEC → 最后调 ASR
```

如果不先完成前三步，后续所有“降噪效果”测试都可能是在错误或过期音频上调参，结论不可信。

## 3. P0：必须先修的问题

### P0-1 ES7210/I2S 输入格式可能从源头错误

当前实现：

- `mic.c` 用 TDM 4 槽初始化 RX，但 `esp_codec_dev_open()` 传入 `channel=2`、`channel_mask=0`。
- 当前 esp_codec_dev 的 ES7210 驱动在“TDM + channel <= 2 + mask=0”时会执行 `bits >>= 1`。
- 即传入 16-bit 后，ES7210 侧可能按 8-bit 配置，而 I2S RX 仍按 16-bit 读取。

原厂同板型 `xiaozhi-esp32` 的做法不同：

- 板级输入/输出采样率为 24kHz。
- `BoxAudioCodec` 打开输入时使用 `channel=4`。
- 通过 `channel_mask` 明确选择 TDM slot 0 和 slot 1。
- 原厂注释明确 TDM slot 顺序为 `MIC1, MIC3, MIC2, MIC4`。

这不是普通调参差异，而是输入格式契约不同。必须先修正并用原始 PCM 验证，否则噪声、幅度异常、AGC 误判都可能由格式错配造成。

**建议方案：**

1. 先完全复用原厂 codec 打开方式：`channel=4 + mask(slot0|slot1)`。
2. 先按原厂 24kHz 采集，再对选出的 M/R 通道同步重采样到 16kHz后喂 AFE。
3. 增加诊断模式，分别导出 4 个 TDM slot 的 10 秒 WAV。
4. 对四路计算 RMS、峰值、削波率、互相关，确认哪个是主麦、哪个是播放参考、是否真的存在第二个独立空间麦克风。
5. 未完成通道实测前，文档中不要再宣称“双麦波束已启用”。

### P0-2 AFE 环形队列会输出旧音频并静默丢新音频

`afe.c` 当前持续运行 feed/fetch，fetch 无条件把增强音频写入一个约 20 秒的 Ringbuffer。没有录音消费者时，队列会逐步填满；`xRingbufferSend()` 的返回值未检查。

后果：

- 待机一段时间后开始录音，`afe_read()` 会先读到待机期间的旧音频。
- 队列满时，新生成的实时音频会发送失败，但没有日志、计数或告警。
- 问答、声纹录入也共用该队列，同样可能拿到旧内容。
- TTS 播放结束后自动续录时，可能把设备自己的回答残留录进去。

**建议方案：**

1. AFE fetch 任务成为唯一输出拥有者，不允许多个消费者直接争用同一个历史 Ringbuffer。
2. 输出 FIFO 只保留 200–500ms，满时明确“丢最旧保最新”，并记录 overflow 计数。
3. 每次录音/问答/声纹开始时发出 generation reset，由 fetch 所在线程安全清空 AFE buffer 和输出 FIFO。
4. 第一帧必须携带采集单调时间戳，录音层检查连续性和延迟。
5. 所有 `xRingbufferSend`、任务创建和读取超时都必须检查返回值并进入可见故障状态。

xiaozhi 当前 AFE 实现已经有 generation、deferred reset、单 fetch owner 的模式，可以直接借用，不建议继续扩展现在的简化 Ringbuffer 方案。

### P0-3 离线容量计算错误，当前只能保约 13–15 分钟

当前落盘格式是 16kHz、16-bit、单声道 PCM：

```
32000 B/s × 20s = 640000 B/段（约 625KB）
25MB / 32000 B/s ≈ 13.1 分钟
27MB / 32000 B/s ≈ 14.7 分钟
```

进展文档中的“43 段约 14 小时”是数量级错误：43 × 20 秒只有约 14.3 分钟。

当前 `queue_save()` 在剩余空间不足 3MB 时直接拒绝保存新段，实际行为是“保旧丢新”，与明确要求“删最旧、保最新”相反。

**建议方案：**

1. 立即改为 Opus 16kbps 左右，30 分钟约 3.6MB，25MB 理论约 3.6 小时。
2. 若目标确实是 6–8 小时，需要约 8–10kbps，必须实测 ASR 字准率后才能决定，不能只按容量选码率。
3. 队列满时按持久化序号删除最旧的完整 `.ready` 文件，再原子提交最新分段。
4. 屏幕明确显示“可离线录制剩余时长”，不要只显示文件数。
5. 修正文档中所有 PSRAM/Flash 容量估算。

### P0-4 队列没有单写者，存在重复上传、半文件读取和数据丢失窗口

当前路径中：

- `record_task()` 结束时同步调用 `queue_flush()`。
- 独立 `flush_task()` 每 30 秒也会调用 `queue_flush()`。
- 两者没有互斥，可能同时枚举并上传同一文件。
- `queue_save()` 直接创建最终 `.wav` 文件，周期性 flush 可能在写完前看到它。
- `fwrite()` 返回值未检查，没有 `fflush/fsync`，没有 `.part -> rename` 原子提交。
- 异常大小文件由上传线程直接删除，掉电造成的半文件没有隔离或恢复策略。
- 文件名使用开机后的毫秒时间，重启后可能与旧离线文件重名并被 `wb` 覆盖。
- HTTP 202 后设备立即删文件，但服务端没有 segment id 幂等去重。

**建议方案：**

建立一个唯一 Queue Worker：

```
录音任务 -> 提交内存块/编码帧
Queue Worker -> .part 写入 -> fsync -> rename .ready
Queue Worker -> 串行上传 -> 校验 ACK(session_id, seq, sha256) -> 删除
```

服务端按 `(device_id, session_id, seq, sha256)` 幂等接收；重复上传返回同一 ACK，不重复生成日报和推送。

### P0-5 初始化失败后仍继续运行，录音可能“看起来开始了”但没有有效数据

当前行为：

- `mic_init()` 失败只打印日志，主流程继续。
- `queue_init()` 返回值被忽略。
- `afe_init()` 失败只打印 warning，按键/触摸任务仍启动。
- `afe_read()` 对未初始化的 Ringbuffer 没有空指针保护。
- 多个 `xTaskCreate()` 返回值未检查。
- 串口 `HUB` 命令会再次调用完整 `recorder_init()`，可能重复创建 AFE、按钮、触摸和补传任务。

**建议方案：**

- 录音核心任一初始化失败都 fail closed，进入明确的“录音不可用”页面。
- `recorder_init()` 改成严格幂等，URL 修改与硬件初始化拆开。
- 增加启动自检结果：codec、AFE、storage、WiFi、队列、内存分别上报。

## 4. P1：除噪与远场质量问题

### P1-1 当前不是“双麦波束”，而是单通道 AFE

`afe.c` 当前把两路输入中的左声道抽出来，以输入格式 `"M"` 喂给 AFE；AEC 明确关闭。代码注释称“双麦在 ES7210 内部混合”，但没有硬件通道实测或原理图证据支持。

当前可信结论只能是：

- 录音链路正在使用一个主麦通道。
- AGC 已开启，压缩增益 12dB。
- VAD 已关闭。
- NS 是否启用依赖 `afe_config_init()` 默认值，代码没有显式设置，也没有打印实际 pipeline。
- AEC 未启用。

日志却打印 `aec+ns+agc+wakenet`，与实际配置不一致，应立即改为打印真实配置。

### P1-2 AGC 不是降噪，固定 30dB 模拟增益 + 12dB AGC 可能同时放大底噪

远场 3–5 米时，语音到达麦克风的直达声很弱。单纯提高模拟增益和 AGC 会同时放大空调、键盘、混响和 ADC 底噪，并不能恢复已经被噪声淹没的语音。

应先测原始信号，再决定：

- ES7210 模拟增益建议从 18/24/30dB 三档 A/B。
- AGC 必须记录输入/输出 RMS、削波率、增益轨迹。
- 削波率建议小于 0.1%，正常说话峰值留 6–12dB headroom。
- NS 模型至少比较 WebRTC NS 与 NSNet2；不能只凭“听起来更安静”判断，要看 ASR CER。

### P1-3 AEC 与录音降噪应分开处理

录音模式不播放声音时，AEC 没有收益；问答播放、barge-in 或边播边听时才需要 AEC。

建议：

- 录音模式：主麦 → DC/HPF → NS → 可控 AGC，不启用 AEC。
- 问答监听/播放：`MR` 输入 → AEC → NS → VAD/WakeNet。
- 问答结束恢复录音前，必须清空 AFE 和输出 FIFO。

如果 v1 首要目标是“稳定录音”，可以暂时取消播放期间的 barge-in，把 AEC 调优放在录音链稳定之后。

### P1-4 3–5 米远场可能超出板载拾音的物理能力

2026-11-18 的真实结果已经表明：近场完整，3–5 米远场碎片化。降噪可以改善稳态噪声，但不能从低于噪声地板的信号中恢复完整语句，也不能消除办公室混响。

建议同时做两条路线：

1. 设备摆到真实对话中心，目标距离先收敛到 0.5–1.5 米。
2. 若必须覆盖 3–5 米，评估外接有线领夹/会议麦或真正的双麦阵列，不要把全部希望放在软件 AGC。

## 5. P1：服务端和产品链路问题

### P1-5 阿里返回空结果时自动回退 Whisper，会重新引入已知幻觉

进展文档已经验证：噪声段上阿里返回空是正确行为，而本地 Whisper 会产生“点赞订阅”等幻觉。但当前 `_run_asr()` 把“阿里空结果”当异常并自动回退 Whisper。

建议：

- 阿里明确返回空时直接标记 `no_speech`，不要回退。
- 仅在网络/鉴权/服务故障时考虑回退。
- Whisper 回退前必须通过严格 VAD，并设置 no-speech/entropy/重复文本过滤。

### P1-6 20 秒分段被当成独立会话，服务端会重复更新日报并推送

设备没有把一个用户录音会话的 `session_id/seq/end` 传到服务端。每个 20 秒 WAV 都生成新的服务端 session，处理完成后立即重写日报并推送唐僧。

建议：

- 分段只作为传输单元，不能作为业务会话。
- 增加 session manifest：开始时间、seq、结束标记、总时长、哈希。
- 服务端收齐或超时封口后再做一次 ASR/结构化；日报仍按 18:30 推送，不按每段推送。

### P1-7 源码、部署包和实际服务缺少可复现边界

- `/Users/xspace/ESP32Dev` 根目录不是 Git 仓库，自研固件和 Hub 没有统一版本历史。
- `hub/` 与 `deploy/pkg/mywork-hub/` 已明显漂移；部署包缺少最新问答、声纹和 pipeline 改动。
- 当前设备固件缺少可查询的 git SHA/build id/config hash。

建议：

- 将自研 firmware、hub、docs 纳入一个根仓库，排除 build、密钥和录音数据。
- 部署包由脚本从同一提交生成，不允许手工复制。
- 固件 `STATUS` 输出 firmware version、git SHA、sdkconfig hash、AFE 配置摘要。

## 6. 建议整改顺序

### 第一阶段：录音正确性（最高优先，先不要调“听感”）

1. 对齐原厂 ES7210 打开方式，做 4-slot 原始采样诊断。
2. 修复 AFE 生命周期、旧音频清理和 overflow 统计。
3. 让录音核心初始化失败时 fail closed。
4. 保留 raw/processed 双轨测试输出，确认时间和内容完全对应。

**阶段出口：** 按下录音后 300ms 内开始的数据必须是当前声音；连续 30 分钟无缺帧、无旧音频、无未知静音填充。

### 第二阶段：可靠缓存和上传

1. 接入 Opus。
2. 单 Queue Worker + 原子文件 + 持久化序号。
3. 实现删最旧保最新。
4. 服务端增加幂等 ACK 和 session/segment 协议。

**阶段出口：** 断网 30 分钟、重启、网络抖动后，服务端收到的分段数、顺序、时长和 SHA256 全部一致。

### 第三阶段：除噪参数矩阵

固定同一批语料和位置，至少录以下条件：

| 距离/环境 | raw | NS | NS+AGC | AEC+NS（播放场景） |
|---|---:|---:|---:|---:|
| 0.5m 安静 | 必测 | 必测 | 必测 | 可选 |
| 1.5m 空调 | 必测 | 必测 | 必测 | 可选 |
| 3m 办公室 | 必测 | 必测 | 必测 | 可选 |
| 1m 设备播报 | 必测 | 必测 | 必测 | 必测 |

每组记录：

- 输入/输出 RMS、峰值、削波率、噪声地板。
- SNR 或 SI-SDR 改善。
- 阿里 ASR CER/关键词召回率。
- CPU、内部 RAM、PSRAM、AFE overflow、I2S read error。

最终以“ASR 字准率提升且不明显吃字”为标准，不以波形更小或主观更安静为标准。

### 第四阶段：长稳与故障注入

- 8 小时录音 soak，WDT/Guru/重启为 0。
- 每 5 分钟断网/恢复一次，持续 1 小时。
- 写文件中途断电，重启后不删除最后一个完整段。
- Flash 满、Hub 500、认证失败、DNS 失败分别测试。
- 队列积压时 UI、按键、触摸仍能响应。

## 7. 暂时不要优先做的事情

在上述 P0 未关闭前，不建议继续投入：

- 界面美化。
- 声纹准确率调优。
- 说话人左右方位推断。
- 边录音边唤醒/播放打断。
- 更多 LLM 汇总模板。

原因很简单：原始录音如果时间不对、格式不对或已经丢段，上层功能越多，只会把不可靠结果包装得更复杂。

## 8. 建议的第一批代码改动范围

第一批只动录音核心，建议控制在以下文件：

- `firmware/wifi-provision/main/mic.c/.h`：ES7210 通道与采样格式。
- `firmware/wifi-provision/main/afe.c/.h`：单 owner、reset generation、真实 pipeline、overflow 指标。
- `firmware/wifi-provision/main/recorder.c/.h`：会话状态、开始时清空、错误闭锁、session/seq。
- `firmware/wifi-provision/main/queue.c/.h`：单写者、原子写、最旧淘汰、幂等上传。
- `hub/scripts/public_relay.py`：唯一文件名、幂等 ACK、会话封口。
- `hub/mywork_hub/pipeline.py`：禁止阿里空结果回退 Whisper。

第一批不改 UI 风格、不改日报模板、不改声纹模型，避免扩大验证面。

## 9. 验收门槛

只有同时满足以下条件，才能称为“录音核心稳定”：

1. 按键开始后的音频时间偏差小于 300ms，无待机旧音频。
2. 30 分钟连续录音 PCM/解码后样本数误差为 0，或协议允许范围内有明确可解释的 codec padding。
3. 断网 30 分钟后自动补传完整率 100%，顺序正确，无重复业务会话。
4. 满盘策略实测为删最旧保最新，且 UI 明确告警。
5. 8 小时无 WDT、Guru、任务静默退出、持续内存下降。
6. 1.5 米空调环境中文 CER 达到产品目标；3–5 米如果未达标，要明确改摆位或加外接麦，不能用 AGC 掩盖。
7. 设备、源码、部署服务均可通过版本号和哈希对应到同一发布记录。
