# 录音保存失败与全量文字导出

日期：2026-11-20（Asia/Shanghai）

## 用户目标

优先保护现有录音，查清设备反复显示“录音保存失败”的实际原因；核对设备待传录音、服务器原始音频和既有转写，导出全部可恢复的完整文字，不以工作摘要或过滤结果替代原始转写。

## 执行约束

- 先只读读取串口状态和错误日志，不复位、不烧录、不格式化、不发送清空命令，避免丢失尚在 RAM 的片段。
- 原始音频和导出结果放在 git 忽略的 `out/` 私有目录，不提交用户录音或完整对话到仓库。
- 服务器 `05_语音工作日志` 只读核对；转写导出到单独的恢复目录，避免和 Hub 写入冲突。
- 按原始音频逐个核对已有完整 ASR 段；没有完整转写的音频另行识别，失败、静音、损坏、缺片均明确标注，不编造内容或姓名。
- 发现原因后先验证修复，涉及设备重启前先保护可获取的 Flash 和 RAM 数据。

## 完整文字导出口径

- 设备正式及可解码的临时 Opus、服务器原始 `dev_*.wav`、原始 `ask_*.wav`、原始 `enroll_*.wav` 分组列出；声纹样本独立附录。
- 排除规范化 `.16k.wav` 重复副本及机器生成的 `.tts.wav` / `.24k.pcm` 回答，不将其冒充人说的话。
- 按文件内容 SHA256 去重，保留所有来源映射。重新调用现有阿里 ASR 接口，逐文件保存未经过工作过滤、DeepSeek 或纠词的原始返回文字；失败最多重试 3 次。
- 为每个源文件记录音频可解码情况、时长、能量、完整性、识别状态；空结果只标记“未识别出文字”，不能推断一定没有声音。分片时间和设备时钟不等同精确逐字时间或无缺录证明。
- 所有私人音频、全文和 ASR JSON 仅存 `out/recording-recovery-20261120/` 及服务器独立 `.recovery/20261120/`，不纳入 Git。

## 根因复现与修复

- 用 ESP-IDF 原版 FatFs R0.16 + ASan/UBSan，在备份镜像的内存副本复现：根目录 `.part` 重命名、下一段 `.part` 创建均返回 `FR_DENIED(7)`，而空闲仍为 19963904 字节。原始镜像 SHA256 未改变。
- 新录音写入 `/fat/rec/` 可增长子目录，扫描/计数/上传同时兼容旧根目录。服务端 segment ID 仍取原 basename，不因目录改变产生新 ID。
- 开机只恢复页 CRC、序号、OpusHead、最终 EOS 均完整的 `.opus.part`，并检查目标不存在；不删除不完整临时文件。124 个真实 Opus（含 1 个临时文件）均通过校验，截断/CRC/序号/尾部垃圾测试均拒绝。
- 同一 FatFs 内存盘验证：保留旧文件场景新增 200 个长文件名成功；清空的**内存副本**场景写入、fsync、rename、读回 360×51717 字节（2 小时分段容量）成功，尚余 6242304 字节。此项是目录/容量回归，不等于实机连续两小时续航验收。
- 保存失败界面按编码、目录、容量、创建、写盘、重命名区分，明确未保存尾段只在 RAM，不能误报为仍在正常录音。

## 实机验证与音频并发发现

- 仅写 app 分区已通过 esptool 读回哈希；首轮实机录制 85.0 秒，4×20 秒 + 5 秒尾段均保存到 rec 子目录，124 → 129 个正式录音，无保存失败。旧完整临时文件已恢复为第 124 个正式录音。
- 正式 HTTPS 入口认证已核验；设备补传实际收到 HTTP 202 并在核对 segment ID、字节数、SHA256 回执后减少队列，证明根目录旧录音仍能上传。
- 录音+HTTPS 成功上传并发时捕获 39 条 AFE(FEED) 缓冲满告警，不能将“落盘成功”当成“采集零丢帧”。现有默认 AFE 内部增强任务调度参数未显式设置，feed 在 core0，网络也在 core0；计划将内部增强任务固定到 core1、优先级 9，并加大 AFE 突发缓冲、用 PSRAM 放输出缓冲，随后重复实机测试。
- 目前完整转写覆盖备份快照：429 源文件、407 个唯一内容，406 份可解码音频合计 7333.733625 秒。原音 ASR：182 份有文字、224 份无文字；零字节内容 1 份对应 4 个零字节源文件。重新识别请求错误已重试完成，不将无文字等同于静音。
- 音量增强复核额外 7 份返回候选，已与原音识别分开标记，未通过人工核听；其余 217 份仍无文字。设备单独导出有效音频 2429.60 秒，约 40 分 30 秒。

## 屏幕阻塞风险与在途尾段保护

- 后续并发测试 AFE(FEED) 满告警降至 0，但 I2S DMA 队列溢出计数仍增加，不能宣称音频零丢帧。增加 DMA 缓冲、IRAM-safe ISR 和计数诊断，继续将采集 feed 移到音频专用 core1 优先级 12（fetch10 / enhance9）。
- 测试中停止后长时间 `recording=0 busy=1`，AFE 和串口仍工作。发现采集任务直接调用同步 `display_brightness()`，且该 SPI 参数发送未与颜色 DMA 的事务回收串行；屏幕操作存在阻塞采集/收尾的风险。
- 将亮度 API 改为原子投递最新值，独立低优先级显示控制任务在同一 flush 锁下发送参数，等待颜色 DMA 带超时。采集和按键调用者不再等待屏幕 SPI。
- rc3 下多次熄屏/亮屏与录音/上传并发的收尾验证正在进行。新增 ISR 计数揭示：AFE 输出不再溢出并不能证明 I2S 无丢帧，DMA 队列仍有可测溢出；记录容量与音频完整率必须分开验收。
- 继续采用 ESP-IDF S3 的 `SPIRAM_XIP_FROM_PSRAM`（同时将指令和只读数据移入 PSRAM）。SDK Kconfig 明确此组合允许 Flash 操作期间继续执行，不再依赖 Flash 中代码/常量；这是针对 Flash 落盘和实时采集冲突的候选修复，需检查 PSRAM 余量、启动、并发 DMA 计数。若无法通过则回退，不宣称通过。
- 为保护当前测试未落盘尾段，尝试 USB-JTAG 暂停/读内存/恢复执行。状态区读到缓冲长 112000 字节（3.5 秒），但调试日志报告 RTC WDT core/RTC reset，导出的 PCM 信号与此前电平明显不一致，**不能确认为有效录音，不计入全文**。只保留为取证文件；没有擦写 Flash。首次串口和此次调试均可能影响未落盘 RAM，不能承诺其恢复。

## rc4 反例与下一步

- rc4 已仅烧 app，哈希核验成功；80 秒墙钟录制只采集 72.9 秒，RX DMA 溢出在测试期间增加，未通过音频完整率验收。保存和收尾均成功，说明目录/屏幕修复与音频丢帧是独立问题。
- 本地 IDF `spi_flash_os_func_app.c` 证据：即使代码/只读数据在 PSRAM，只要还存在 Flash mmap，写/擦仍会禁缓存/调度。ESP-SR `esp_srmodel_init()` 将整个模型分区 mmap；唤醒模型仍留 Flash 是待验证的残留路径。
- 计划在 AFE 建立前，将 SDK 已解析的模型文件名和载荷复制到对齐的 PSRAM，全部复制成功后才解除原模型 mmap；不改第三方组件、不更换唤醒模型，不启用未核验芯片支持的 Flash auto-suspend。随后重测采样时长、DMA 增量和 PSRAM 余量；不通过就明确保留未解决结论。
