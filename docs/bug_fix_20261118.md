# 2026-11-18 录音、降噪与 WiFi 稳定性修复

## 问题描述

1. ES7210 输入设备以 `channel=2` 且未指定通道掩码打开，在当前 `esp_codec_dev` 的 TDM 配置路径中可能把 16-bit 输入错误配置为 8-bit，造成底噪、失真和识别率下降。
2. AFE 输出使用 20 秒环形缓冲且空闲时持续写入。开始录音、问答或声纹采集时可能先读到历史音频；缓冲满时发送失败未检查，会静默丢弃最新音频。
3. 录音双缓冲的保存消息发送结果未检查，保存超时后仍可能复用正在写盘的缓冲；初始化失败也没有阻止录音入口继续工作。
4. 离线队列缺少单写者互斥和原子落盘，文件写入、HTTP 分段发送和上传删除条件不够严格，断电或并发补传时存在损坏、重复或误删风险。
5. WiFi 连接由多个状态变量和多个调度入口共同驱动，可能同时创建连接任务；瞬时断开事件会提前判定连接失败，固定等待又使重连缓慢且不可预测。
6. 阿里 ASR 返回空文本时被当作服务失败并回退 Whisper，纯噪声可能因此被 Whisper 误识别成文本。
7. 实机首轮验证曾出现一次 `LoadProhibited`：补传任务在 6 KB 栈上放置约 4.6 KB 文件列表，叠加 HTTP/文件系统调用后导致栈破坏。

## 解决方案

- 麦克风按 ES7210 TDM 实际格式使用 4 通道打开，并显式选择有效输入 slot；保持 16 kHz 输出链路，避免在本次稳定性修复中引入未经验证的重采样。
- AFE 明确开启降噪，缩短输出缓冲，增加开始采集前的同步清空；缓冲满时丢弃最旧数据并保留最新数据，同时记录溢出计数。
- 录音保存任务改为可靠交接：检查队列发送和任务创建结果，未完成写盘时不复用缓冲；初始化失败时关闭录音功能；初始化入口幂等。
- 队列改为单后台上传者、互斥访问、`.part` 原子写入与重命名、完整写入检查、部分 HTTP 写处理，并优先删除最旧已完成文件以保留最新录音。
- 补传排序列表移到 PSRAM，补传任务栈增至 8192 字节，消除实机定位到的栈溢出。
- 损坏文件隔离和上传成功使用独立状态码；`.bad` 隔离成功后不再误走“上传成功后删除原文件”路径。
- 录音优先级高于后台补传：录音忙时不启动新补传；已在进行的 HTTP 上传在 16 KB 分块边界检测录音状态并按 `UPLOAD_PAUSED` 退出，不再误触发 IP 兜底。
- CPU 主频从 160 MHz 提升到 240 MHz，避免 WebRTC NS + WakeNet + AGC 与 WiFi/TLS 并发时 AFE 来不及处理。
- WiFi 改为单连接任务所有者，连接请求去重，区分主动切换和真实掉线，清理事件位后重试并采用退避；连接进行中不轮换网络。
- 阿里 ASR 空结果标记为 `no_speech`，只有网络或服务错误才回退本地 Whisper。

## 声纹录入、分段识别与真实波形修复

### 问题描述

1. 声纹页点击后未先占用状态，快速连续点击可创建多个录入任务；取消时又会在旧任务退出前把 UI 改为空闲。
2. 录音收尾只等待 3 秒，写盘/补传稍慢就误报声纹录入失败；任务创建返回值未检查。
3. 声纹上传只写一次 HTTP body，部分写入也可能继续读响应；删除先清本地再请求服务端，失败会造成两端不一致。
4. 设备和服务端都缺少录入质量门槛，静音、过短、严重削波样本可能入库。
5. Hub 录入音频写进 Mywork inbox 且不清理；声纹库无锁、非原子、权限过宽，每个名额只有一个整体模板。
6. 流水线对整段 WAV 只识别一次，然后给全部 ASR 段写同一个 speaker，多人会话必然误标。
7. 录音页波形由 RMS 比例驱动固定正弦动画，不是当前 PCM 的真实包络，安静和说话看起来变化不明显。
8. 实机启动日志发现 AXP2101 上电残留 PWRKEY IRQ 会被当成新短按，开机后可能自动开始录音。

### 解决方案

- 声纹录入/删除共用单任务占用状态；点击名额时先原子 claim，再创建任务，失败立即回滚。
- 录入中普通触摸忽略，仅底部明确“取消”区域设置 abort；由任务统一释放状态和缓冲。
- recorder 收尾等待从 3 秒提高到 30 秒，并允许取消；设备侧增加时长、RMS、有效帧和削波检查。
- 声纹 HTTP body 循环写满后才读取响应；删除改为后台事务，服务端成功后才删除本地 NVS。
- 服务器用临时目录转码，处理结束自动删除源 WAV；完整校验 `Content-Length`。
- 声纹库增加线程锁、文件锁、临时文件 + `fsync` + `os.replace`，目录/文件权限为 0700/0600。
- 8 秒录音切为多个 2 秒窗口，保存多模板和中心向量；同 slot 重录原子替换。
- ASR 每段取 1.5–3 秒上下文分别识别；高置信直接认定，中置信仅在前后 10 秒高置信投票一致时认定，其他归“其他人”。
- 录音波形按每次读取的 100ms PCM 横向分桶，绘制真实短时 RMS 包络并使用 dBFS 对数映射和平滑回落。
- 按键任务启动后延时 600ms 并清空 AXP2101 历史 IRQ，避免上电事件触发录音。

## 录音中下面按键无法熄屏（2026-11-18）

### 问题

录音时按下面的 KEY1 后，背光短暂关闭，但录音任务下一次读取 100ms 音频就会调用 `screen_wake()`，导致屏幕马上重新亮起。

### 修复

手动录音模式尊重用户设置的 `s_screen_off` 状态；只有自动采集模式在检测到近期语音时才自动唤醒屏幕。熄屏期间继续采集和写盘，不影响录音数据。

### 验收

- [ ] 再次单击 KEY1 恢复亮屏，录音界面在下一帧刷新。

## 录音波形、停止规则与语音问答稳定性（2026-11-18）

### 问题

- 录音任务以 10Hz 整屏绘制波形，屏幕 SPI 刷新会挤占音频处理时间；波形又取自 NS/AGC 输出，AGC 会让不同外界音量显示得过于相似。
- 触屏单击会停止录音，下面按键长按目前通过高频整屏动画反馈，均可能干扰录音。
- 录音中触屏 PTT 被 recorder 拒绝；唤醒词在收尾期间也会因 busy 被丢弃。
- 问答采集阶段错误显示“回答中”，任务创建失败或离线时状态恢复不完整。
- WiFi 连接等待可能把已置位的旧 GOT_IP 事件误当成本轮成功；断开后旧 IP 仍留在状态页，且连接成功后 WiFi 始终常开。

### 解决方案

- AFE feed 线程产生原始麦克风 RMS 历史；新增低优先级、5Hz UI 任务独立刷新波形。录音任务不再绘制，熄屏时不 flush。
- 触屏点击不再控制录音；下面按键短按只切屏、长按 3 秒请求封存并停止，屏幕关闭不改变录音状态。
- PTT 和唤醒词先请求录音任务封存当前片段，收尾完成后再进入问答；只在此前确实录音时于问答结束后恢复。
- 分别显示“请说话”“回答中”“无网络”，检查问答任务创建结果，避免问答状态挂死。
- WiFi 连接轮次同时核实 GOT_IP 事件位和实时连接标志，断线清理 IP；配网保持 WiFi 常开，正常连接后启用 `WIFI_PS_MIN_MODEM`，降低待机耗电。

## 全链路核验与问答转唐僧（2026-11-18）

### 核验结论

- 录音日报链路：ESP32 本地 WAV 队列 → `POST /v1/upload` → 阿里 Paraformer（`ASR_PROVIDER=aliyun`）→ DeepSeek 段级过滤 → DeepSeek 日报汇总 → 写入 Mywork → OpenClaw `tangseng` 通知，代码链路完整；公网和 6.6 的 `/health` 均返回正常。
- 旧问答链路实际是：`POST /v1/ask` → 阿里 ASR → DeepSeek 直接回答 → 阿里 TTS → ESP32 播放。虽然存在 `ask_tangseng()`，但原实现没有调用它，因此不符合“先整理问题再交给唐僧回答”。

### 修复方案

- 问题音频继续由阿里 Paraformer 转文字。
- 新增 DeepSeek 快模型问题整理，只改写问题，不回答、不执行转写内容中的指令。
- 将整理后的问题交给唐僧 OpenClaw；唐僧不可用时才降级到 DeepSeek 问答，并记录降级原因。
- 唐僧/降级回答继续由阿里 NLS TTS 合成为音频，转换为 ESP32 当前 16kHz 双声道 PCM 后返回。

### 真实问答核验发现（2026-11-18）

6.6 上 `openclaw agent --json` 的文本位于 `result.payloads[].text`，且输出是多行 pretty-printed JSON；旧解析器只读取顶层 `payloads` 并按行解析，会把唐僧的成功回答误判为空并错误降级到 DeepSeek。

修复：先解析完整 stdout，再按行兜底；同时兼容顶层和 `result` 容器，并保留 `finalAssistantVisibleText` 作为最后兜底；部署后必须重新用有声 WAV 验证日志出现“唐僧回答”和 TTS 返回音频。

另外，无有效语音时 `/v1/ask` 改返回 HTTP 422，而不是用 200 携带 JSON；固件只有收到 200 才播放 PCM，避免把错误 JSON 当成声音播放。
