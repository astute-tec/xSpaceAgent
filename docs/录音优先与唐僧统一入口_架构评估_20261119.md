# 录音优先与唐僧统一入口：架构评估

日期：2026-11-19（Asia/Shanghai）

## 本次范围

用户提出让小智专注可靠录音与音频上传，由唐僧侧统一完成转写、说话人识别、问答与工作总结。本次先评估分工、延迟收益与迁移方案，形成可执行设计；不在评估阶段修改线上流程或重启正在录音的设备。

## 1. 结论

赞成“设备专注可靠录音、唐僧侧统一处理”的方向，但不建议把网络接收、文件队列和重试也交给大模型代理执行。保留唐僧主机上的轻量 Hub，作为唐僧的音频接入服务；用户感知仍然是“直接交给唐僧”，无需再建一套服务或更换设备域名。

当前阿里 ASR、DeepSeek 和唐僧调用本来就都在服务端，并不是 ESP32 依次访问三个平台。真正需要调整的是：减少不必要的串行模型调用、区分录音和问答调度、可靠处理队列、压缩传输、收到首段音频就播放。只换入口名字或重新刷机，不会自动解决延迟和卡顿。

本次只形成架构分析与迁移设计，没有改动固件/后端代码、重启服务、打开设备串口或烧录。以下代码事实以本次工作区核对为准；现场时间来自此前的实机验证记录，不代表本轮重新实测。

## 2. 当前实际实现

### 2.1 问答

```text
设备录完整段 WAV → POST /v1/ask → 唐僧主机 Hub
  → 阿里 ASR → DeepSeek 整理问题 → 唐僧回答
  → 阿里 TTS → ffmpeg 转 16kHz/双声道/16bit PCM
  → 设备下载完整音频 → 播放
```

- `hub/mywork_hub/ask.py:answer_question()` 先执行 `_normalize_question()`，再调用 `openclaw agent --agent tangseng`；唐僧失败后才使用 DeepSeek 降级回答。
- `hub/scripts/public_relay.py:process_ask()` 在 TTS 前发布回答文字；目前文字不是逐 token 流式返回，唐僧调用仍等待完整 CLI JSON 结果。
- `firmware/wifi-provision/main/recorder.c:ask_send_task()` 提交整段音频后轮询状态，每轮重新建立 HTTPS 客户端；文字可先显示，音频仍完整下载后播放。
- 当前 `ASK_JOBS` 是内存字典，服务重启后丢失；异步接口不等于持久队列。

### 2.2 日常工作录音

```text
设备每约 20 秒封装 PCM WAV → 本地队列 → /v1/upload
  → Hub 保存原始音频并确认接收
  → ASR → DeepSeek 工作内容过滤 → 服务端声纹比对
  → 写会话记录 → 重建当天日报 → 推送唐僧
```

- `public_relay.py:process()` 对每个上传片段执行一次日报重建和推送，并用 `PROCESS_LOCK` 串行处理普通录音。这会让持续录音产生大量重复总结和通知，是需要优化的调度点；本轮没有证明它是某次设备卡死的唯一原因。
- 声纹实际在 `hub/mywork_hub/voiceprint_np.py`，使用 MFCC 均值/标准差与多模板比对，不是已经验收的神经网络说话人模型。三个姓名同步成功不等于复杂噪声、远场或多人交叠识别准确率已经达标。
- `report.py` 的提示词还保留“两个人、按左右位置推测姓名”的旧规则，聚合输入也未完整保留逐段实名声纹信息。应删除身份猜测、贯通逐段识别结果，不能让总结模型覆盖或臆造发言人。

## 3. 延迟证据与判断

来源：`docs/声纹与语音问答现场修复_20261119.md`，job `ae1f6c9053c84c60912b66112903409f`。

| 项目 | 已有观测 |
|---|---|
| 问题采集 | 约 3.2 秒，裁剪后 WAV 80640 字节 |
| 阿里转写 | 正确识别“今天的工作进展怎么样？” |
| 唐僧调用 | 约 3.1 秒返回 |
| Hub 处理至 TTS 完成 | 约 7.0 秒 |
| 从提交到设备收到文字 | 约 14.3 秒 |
| 从提交到开始播报 | 约 70.4 秒 |
| 回答音频 | 731572 字节，当前是双声道 PCM |

这些时间不全处于同一计时区间，不能直接加减成精确链路分解；足以说明服务端生成完成后，音频传输和整包缓冲仍有显著等待。TLS 重连、设备网络/内存调度、隧道链路各占多少，还需要分阶段打点，不能直接认定为某一个网络组件的问题。

取消前置 DeepSeek 整理值得做，能省一次正常调用及其超时风险；但不能据此承诺把 70 秒降到 3 秒。更大的优化点是压缩音频、连接复用和首段即播。

## 4. 推荐职责边界

| 部分 | 应负责的事 |
|---|---|
| 小智设备 | 持续采集、适度降噪、波形/时间/按键、编码、本地可靠缓存、断网重试、唤醒/问题采集、文本显示、边收边播 |
| 唐僧侧接入服务（沿用 Hub） | 鉴权、流式接收、校验、持久化确认、去重、恢复队列、阿里 ASR/TTS、服务端声纹、任务状态和限流 |
| 唐僧业务层 | 理解问题、查询有权限的项目资料、回答、汇总工作记录；如需 DeepSeek，由业务层统一选择 |
| Hub 文件写入器 | 继续单独写 `05_语音工作日志/`，原子更新，唐僧读取，避免双写冲突 |

设备上传成功后，不再等待 ASR/总结/唐僧通知成功才能释放本地副本；但“成功”必须是服务端已经可靠接收，而不是客户端发送函数返回。

### 4.1 日常录音链路：可靠、异步

```text
麦克风 → 降噪 → 编码 → 本地分段保存
  → 传给唐僧侧接入服务 → 校验并持久化 → 返回确认
  → 设备核对确认后释放对应副本，继续录音

服务端持久队列 → ASR + 逐段声纹 → 工作事实增量归档
  → 定时/按需总结 → 唐僧消费
```

- 不给每个 20 秒片段都重跑完整日报和唐僧通知。建议先按 5～10 分钟窗口做增量整理、重要标记优先，18:30 保留日终汇总；实际窗口可配置。
- 用户问“今天进展”时读取最新增量事实和截至时间，不必等完整日报重新生成；项目全局进展由唐僧查询其已有项目资料。
- 工作过滤不能随问答前置整理一起盲删。可先保留已有过滤器，再比较“唐僧统一结构化处理”的质量、吞吐和成本，最终只留一个工作语义整理环节。
- 普通工作语音中的话都是待记录资料，不能触发代理执行命令。单独的“重要事项记录”使用明确的产品事件类型，经 Hub 单写者保存和确认；不把任意转写当执行授权。

### 4.2 唤醒问答链路：高优先级、尽早反馈

```text
双击上键 / “你好小智” / 长按屏幕
  → 进入同一监听状态，边说边传至唐僧侧
  → 阿里流式 ASR（转写可显示）
  → 用户单击上键提交 → 完成转写 → 原问题直接给唐僧
  → 回答文字立即显示 → TTS 首段到达即播 → 后续音频继续接收
```

- 删除问答主路径中的额外 DeepSeek 问题整理；标点等可用 ASR 能力，含糊处由唐僧追问，不再串行调用一个模型“改写问题”。
- “文字和语音一起”应是同一会话关联、先有先发，而不是等待文字和整段语音都完成再返回。
- 第一阶段即使唐僧只能返回完整文本，也可在文本返回后分句 TTS 和边收边播；不要把 OpenClaw token 流接口尚未核实的能力作为实施前提。
- 传输优先验证单声道，设备播放前再适配 I2S 双声道；压缩编解码与有界播放缓冲要测 CPU、堆内存、欠载和声音质量，避免为降延迟再引入卡死。
- 不宜让实时问答排在大段录音补传之后。基于设备资源预算选择单连接多路逻辑消息或有限连接复用；不能直接堆更多 TLS 连接。
- 无声、断网、唐僧超时分别提供本地可播的明确提示，退出后恢复持续录音。TTS 失败时已收到的文字仍保留，不能假报完整成功。

## 5. 录音可靠性：本次发现的优先问题

### 5.1 已有接收保护要保留，但后台恢复不完整

`public_relay.py:_do_upload()` 已经有这些正确保护：

1. 验证接收长度，用片段 ID 去重并检查哈希冲突。
2. 临时文件写入、flush/fsync、原子 rename、目录 fsync。
3. 完成落盘后才返回 HTTP 202，随后启动后台处理。

不能把现状误写成“服务端尚未落盘就确认”。真正的缺口是：

- 任务仅由 daemon 线程启动，没有持久化任务状态/失败重试/启动恢复扫描；去重命中后直接返回，不重新调度未完成任务。服务重启或处理异常后，原始音频还在 INBOX，但可能永远没继续处理。
- 设备 `queue.c:upload_file_to()` 只凭 HTTP 200/202 判断成功，没有核对响应中的片段 ID、字节数等，随后 `queue_flush()` 删除本地文件。
- `pipeline.ingest(..., keep_audio=False)` 删除转换后的中间 WAV，不删除此处的 INBOX 原始输入；因此既需要处理恢复，也需要按明确保留期清理原始音频，避免服务端长期累积。
- 当前日期取服务端处理时刻。离线隔夜补传必须携带采集时间、时钟可信度、设备/会话/片段序号，否则可能把昨天录音计入今天。

建议接收端在确认前同时保证音频和可恢复任务清单落盘；重启扫描补齐未完成状态。设备校验 `device_id/segment_id/bytes/hash` 的确认后才删对应副本。允许至少一次上传，由服务端幂等处理，避免重复日报和重复通知。业务失败只在服务端重试，不要求设备重复执行整套业务。

### 5.2 全天离线容量目前不成立

按当前代码 `16kHz × 单声道 × 16bit`，PCM 为 32000 字节/秒，即 **115.2 MB/小时**（十进制）。

- 存储分区 `0x19F0000`，约 25.94 MiB；减去代码预留的 1 MiB，尚未计文件系统开销，可用上界约 24.94 MiB。
- 理论连续有声缓存上限约 **13.6 分钟**，实际还受其他文件、文件系统开销和 64 文件枚举上限影响。静音丢弃不能作为全天容量保障。
- 当前满盘删除最早未上传片段，现场确认发生过，属于真实数据损失风险。
- 假设使用 20～24 kbps 的候选压缩码率，8 小时纯音频仍需 **72～86.4 MB**，不含封装和索引；现有容量理想上界也只有约 2.4～2.9 小时。压缩效果和识别质量尚待实测，不能承诺现有硬件全天离线。

推荐把“8 小时连续有声离线”作为明确验收场景，核对是否可扩展本地存储；不支持时应明确容量边界或调整硬件。满盘默认不再悄悄覆盖旧录音：提前显示剩余时长/告警，持续尝试补传；容量耗尽时明确提示无法继续完整保存并记录缺口。覆盖旧数据必须成为用户明确选择，不能默认假装无损。

### 5.3 降噪、声纹与播音期间录音

- 当前 `afe.c` 启用单主麦 NS + AGC + 唤醒，`aec_init=false`；双麦/参考通道的真实接线与参考信号仍需实测核对，不能只按板级配置声明启用 AEC。
- `recorder.c` 播音时虽然继续读麦，但 `s_playing` 跳过写入工作录音。界面“录音中”不等于这段没有录音空档。必须用扬声器播放与外部说话同时发生的回录测试验收 AEC。
- 保守降噪在端侧做，声纹识别推荐放服务端。离线先录音，联网后补做声纹；“断网也立即显示谁在说”是额外端侧模型需求，不应在本次架构调整中默认承诺。
- 固定 5 人，其余归“其他人”。现有 MFCC 方案要做三位已录入人员的交叉盲测、噪声/距离测试、未知人拒识和多人交叠测试，再决定是否换成熟说话人模型；模型替换需考虑现有模板兼容，必要时明确提示重录，不能静默沿用不兼容向量。
- 降噪和压缩统一用真实环境音频比较：可懂度、转写错误、低声漏录、削波与声纹误认。不以波形“看起来平滑”代替音质验收。当前 RMS 静音丢段策略也需测低声，必要时采用保守 VAD 与前后留白。

## 6. 在线与离线能力边界

| 场景 | 设备行为 | 恢复联网后 |
|---|---|---|
| 在线持续录音 | 本地先保存，低优先级上传，确认后释放 | 后端异步重试 ASR/归档 |
| 断网持续录音 | 在已验证容量内继续保存，显示待传及剩余时长 | 按采集顺序幂等补传 |
| 在线语音问答 | 最高网络优先级；文字先展示、音频首段即播 | 等待期间持续记录，不等待业务完成才录音 |
| 离线唤醒提问 | 本地告知“当前离线，暂时无法回答”，继续工作录音 | 默认不自动播报过期问题；是否保留待问由产品明确 |
| 云端服务失败 | 设备继续录音；本地明确失败提示 | 已确认录音由后端恢复任务处理 |
| 存储即将满/已满 | 提前告警；不能宣称无损、不能静默覆盖 | 优先补传并核对缺失区间 |

## 7. 最小迁移次序与验收

1. **先保录音**：修订满盘规则；实现后端可恢复任务、设备核对回执、采集时间元数据和录音健康指标。正常录音时不做网络阻塞/UI绘制/长耗时模型计算。
2. **先做低风险问答减法**：取消前置问题整理；录音按窗口增量归档，问答优先；保留当前设备协议兼容，不强制先刷机才能使用后端改进。
3. **再改传输和播放**：候选编码、长连接/复用、单声道传输、有界流式播放；流式 ASR 减少按键提交后的等待，现有文本滚动保留。资源、重连与欠载通过后才切主路径。
4. **完成录音质量专项**：核实音频通道/AEC、声纹准确性及身份从转写到日报的传递；在线/离线各做不少于 8 小时的稳定性测试。若硬件容量不足，先补足存储，不能用短测代替全天指标。

建议作为待验证目标，而非本次已达成：

- 正常网络、5 秒内简短提问：从上键提交起，首条回答文字 P95 ≤ 5 秒，首段回答语音 P95 ≤ 8 秒；另统计长问题/弱网/冷启动，达不到时按阶段日志定位，不隐瞒超时样本。
- 每次记录采集结束、上传完成、ASR 完成、唐僧首字/完整文本（实际支持哪项就记录哪项）、TTS 首包、设备首包、开始播放等时间。以设备单调时钟计端到端，服务端用请求 ID 关联，不直接相减未校准的跨机时钟。
- 录音验收看实际样本序号和时长、丢帧/缺口、掉电未封包尾段恢复范围、未确认片段、缓存占用、队列增长与排空、Flash 写入负荷、heap 最低水位、任务栈和看门狗，不只看界面。
- 注入 WiFi 反复断连、HTTP 超时、重复上传、服务重启/崩溃、满盘、无声、唐僧/TTS 不可用；录音主链不被问答故障拖停。显式长按停止依旧有效。
- 音频落盘与任务结果按保留期清理，声纹只存专用模板库，不写 Mywork；所有工作记录仍由 Hub 单写者原子写，唐僧记忆仅写带 `<!-- voice:auto -->` 的每日文件，绝不写 `MEMORY.md`。

## 8. 官方接口依据与尚需验证的内容

2026-11-19 核对阿里官方文档：

- 实时识别 WebSocket：支持音频流、中间识别结果与显式停止指令，可对应“边说边识别，上键提交”。不同项目、模型和地域的开通情况/热词兼容性需在现有账号验证，不能直接把文件识别接口改名当实时识别。
  - https://help.aliyun.com/zh/isi/user-guide/websocket
- 流式文本 TTS：支持分段文字输入、音频二进制帧输出；文档说明合成音频为单声道，具体格式/音色/采样率要匹配。
  - https://help.aliyun.com/zh/isi/user-guide/streaming-text-tts-wss
- 现有 TTS REST 接口也支持读取过程中处理响应，不一定先换供应商；当前代码 `r.read()` 与后续整包缓存使其没有发挥边收边播效果。
  - https://www.alibabacloud.com/help/en/isi/user-guide/restful-api-3

这些是实现可行性的依据，不是本项目流式链路已经联通的证明。Opus 等候选编码在当前 IDF/AFE/LCD 并行负载下的资源、声音质量和稳定性尚未做本轮实机验证；OpenClaw 当前部署是否支持稳定的 token 流输出也需单独核实。
