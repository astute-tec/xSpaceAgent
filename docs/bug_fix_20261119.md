# 录音卡顿与上键问答修复 · 2026-11-19

## 现场复查

设备串口在本次检查时仍有运行日志，`STATUS` 显示 WiFi 已连接、录音状态为 `recording`；Flash 队列约 40 段并出现“flash full，删除最旧段”。因此当前症状不是整机停止运行，而是持续录音时上传队列无法及时排空，Flash 满后按策略丢弃旧录音，用户可能感知为同步/操作卡住。

代码检查还发现：

- 问答持有全局 HTTP 锁后，`esp_http_client_init()` 失败直接退出，没有释放锁，后续网络任务最多等待 70 秒。
- 队列域名请求失败后的 IP 回退绕过全局 HTTP 锁，可能与问答建立并发 TLS 会话。
- 问答音频分块发送未完成时仍调用 `fetch_headers()`，服务端会等待剩余请求体，造成长时间阻塞。
- 上键处理在判断双击前就因 `s_recording` 返回，录音中双击无法唤醒问答。
- 上键单击由独立 400ms 延迟任务判定，点击计数和任务读取之间存在竞态窗口。
- 声纹队列上传未检查 HTTP client 初始化结果，低内存时可能空指针崩溃。
- 队列补传在录音忙时直接返回；连续录音期间不会上传任何已封存分段，约 40 段占满 Flash 后开始删除旧段。

## 修复

- 用统一清理路径释放问答 HTTP client、请求缓冲和 HTTP 锁；请求体未完整发送时立即中止，不等待服务端响应。
- 域名上传和 IP 回退整个流程持有同一把 HTTP 锁；修正队列上传分配失败时的文件/client 清理，并为声纹上传补空句柄检查。
- 上键双击优先识别并调用唤醒问答，可在录音中先封存当前段再提问；录音中的单击仍忽略。点击序列使用临界区保护并从最后一次点击开始等待判定。
- 录音期间队列以较低优先级每轮上传一段；标记正在上传的文件，Flash 满时保留该文件并从其他旧段中淘汰，避免上传/清理竞态。

## 复核补充（卡顿/卡死风险）

复查后确认此前补传改动还引入了两个明显的长阻塞风险：

- 声纹补传持有 FATFS 全局锁执行 HTTP 请求，网络最差时会让录音保存任务等待网络，形成“录音/界面卡住”的表现。
- 录音分段上传域名与 IP 兜底各自允许等待 120 秒；问答与补传共用 HTTP 锁，问答可能在录音期间等待超过一分钟。
- 上传成功后若 2 秒内取不到文件锁，上传文件标记不会清除，队列满时后续清理会一直跳过该段。

本轮调整：声纹文件名在短暂持有 FATFS 锁时复制到本地，HTTP 上传移至锁外；上传后重新加锁删除成功文件。队列上传标记统一在每次请求后清理；普通队列 HTTP 超时调至 25 秒（含域名与 IP 兜底时总上限约 50 秒）。串口回归仍待执行。
